## 四、验证实验（大纲要求）

### 实验 1：主动失效（下架 → 状态立刻刷新）

时间：2026-11-24 23:00

| 步骤 | 结果 |
|---|---|
| 下架前查 1001（已建缓存）| `status=4`、`statusDesc=销售中` |
| 调 `POST /merchant/shows/1001/off-sale` | 成功 |
| **立刻**再查 1001 | **`status=6`、`statusDesc=已下架`** ← 若缓存未删会读到旧值 4 |

**结论**：`evictDetailCache` 生效（Redis + 本地都删，下次读回源拿新状态）✓

**补充**：SQL 直改 `status=4` 不触发失效（本地缓存仍为旧值，5 分钟 TTL 自然修正）—— 符合"只有接口写操作才主动失效"的设计。

### 实验 2：删缓存重建互斥（本地 + Redis 双空 → 100 并发）

时间：2026-11-24 23:00

| 步骤 | 结果 |
|---|---|
| 清空 Redis `cloudticket:show:detail:1001`（本地因重启为空）| key 不存在 ✓ |
| 100 并发同时查 `/user/shows/1001` | 100/100 成功，总耗时 700ms |
| **MySQL general_log 统计详情主查询执行次数** | **2 次**（而非 100 次）|

**结论**：Caffeine `get(k, loader)` 原子加载 + RLock，**100 并发只回源 2 次（拦截 98%）** ✓

> 严格"1 次"未达成：有极小窗口（首个 loader 完成前，第二个线程也查到 Redis miss 并查库）。2 次已证明机制有效；如需绝对 1 次可加"双检"（loader 内先查本地再查库）。

## 五、D3 余量缓存（单级 Redis + TTL 3s）

时间：2026-11-25 20:20

**策略**：单级 Redis，key=`cloudticket:stock:{sessionId}`，TTL 3s + 抖动 0~1s，读写降级。**不用**多级/布隆/逻辑过期（余量每秒变，短 TTL 就够；价值是"削峰"而非"极致快"）。

| 场景 | QPS | 平均耗时 | P95 | 错误 |
|---|---|---|---|---|
| 余量（缓存）| 1794.6 | 43.8 ms | 76.8 ms | 0 |
| A 组基线（直查）| 2917.7 | 17.5 ms | 29.3 ms | 0 |

**功能验证**：

- 票档余量正常返回（A档 501 / B档 392）✓
- 两次读完全一致（缓存命中）✓
- **TTL 验证**：DB `stock` 550→777（`remainStock = stock - sold_count`）→ **3 秒内仍读 501（=550-49）** → **4 秒后读 728（=777-49）** ✓ TTL 生效

**QPS 说明**：本次数字**不可信**——Python 压测客户端（GIL + 短连接）+ 服务已长时间运行（机器状态与 A 组基线时不同）→ 待 JMeter 复测；本次核心验证是"TTL 生效 + 命中一致"。
