# 定时任务设计（系统侧）

> 对应大纲 3.4「系统侧」；P1 只做「开售流转」的简化版，P2/P3 再演进。
> 本文是**实现依据**：写代码时按这里的条件与边界来。

---

## 一、P1：开售流转任务（`ShowStatusTask`）

### 1.1 职责（4 条流转）

| 对象 | 条件 | 变化 | 说明 |
|---|---|---|---|
| 场次 `show_session` | `sale_start_time <= now` 且 `status = 0` | 0 未开售 → **1 销售中** | 到点开卖 |
| 场次 `show_session` | `session_time < now` 且 `status = 1` | 1 销售中 → **2 已结束** | 演完了 |
| 演出 `show_info` | 存在已开售场次 且 `status = 3` | 3 审核通过 → **4 销售中** | 至少一场能买 |
| 演出 `show_info` | 所有场次都 `session_time < now` 且 `status = 4` | 4 销售中 → **5 已结束** | 全部演完 |

> 演出状态是**粗粒度展示**（3 即将开售 / 4 销售中 / 5 已结束）；**精确可售性**判断在「场次 + 时间」，下单接口必须兜底校验（见 1.6）。

### 1.2 实现方式

- Spring `@Scheduled(cron = "0 * * * * ?")` 每分钟一次；启动类加 `@EnableScheduling`；
- 4 条 **UPDATE 条件更新**（不做"先查后改"），重复执行幂等（影响 0 行）；
- 单实例部署无需分布式锁；将来多实例用 ShedLock（P6 再考虑）。

### 1.3 SQL 示意

```sql
-- ① 场次：到开售时间 → 销售中
UPDATE show_session SET status = 1
WHERE status = 0 AND sale_start_time <= NOW();

-- ② 场次：演出时间已过 → 已结束
UPDATE show_session SET status = 2
WHERE status = 1 AND session_time < NOW();

-- ③ 演出：有场次已开售 → 销售中（审核通过态）
UPDATE show_info s SET s.status = 4
WHERE s.status = 3
  AND EXISTS (SELECT 1 FROM show_session ss
              WHERE ss.show_id = s.id AND ss.status = 1);

-- ④ 演出：所有场次都结束 → 已结束
UPDATE show_info s SET s.status = 5
WHERE s.status = 4
  AND NOT EXISTS (SELECT 1 FROM show_session ss
                  WHERE ss.show_id = s.id AND ss.session_time > NOW());
```

### 1.4 边界（必须遵守）

| 情况 | 处理 |
|---|---|
| **停售但没演**（`sale_end_time` 过、`session_time` 未到） | 演出**仍是 4**；前端按时间显示"已停售" |
| **已下架（6）** | **不参与流转**；已售票照常核销（下架 ≠ 取消） |
| **已结束（5）** | 终态，不再变 |
| **草稿/待审核/驳回（0/1/2）** | 不参与 |
| 定时任务延迟（最多 1 分钟） | 下单接口按时间兜底校验，不影响正确性 |

### 1.5 性能

- `WHERE status = ?` 命中 `show_session.idx_show`/`show_info.idx_status_category` 等索引，只扫少量行；
- 每分钟 1 次、影响行数通常 0~几条 → 毫秒级；
- P1 数据量（几百场）无压力。

### 1.6 与其他接口的关系（重要）

| 接口 | 依赖 |
|---|---|
| 用户端列表/详情 | 读 `show_info.status`（3/4/5/6）决定展示 |
| 场次余量 | 读 `session.status` 决定是否置灰/余量清零 |
| **创建订单（P1 下单）** | **必须双保险**：`show.status = 4` **且** `session.status = 1` **且** `now ∈ [sale_start_time, sale_end_time]` |
| 核销 | 校验场次时间（演出结束后不能核销） |

## 二、P2/P3 演进（预留）

| 期数 | 升级点 |
|---|---|
| P2 | 频率提高到 10~30 秒；与缓存预热联动（开售前把演出/余量预热进 Redis） |
| P3 | **Redis ZSet 延迟队列**替代轮询（开售时间作 score，到点触发）；新增「**订单超时取消**」任务（延迟消息 + 定时扫描兜底）；抢票期余量以 Redis 为准 |
| P4 | 每日对账任务（双池库存校准、销量校准）、开售提醒扫描 |

## 三、命名与落位

```
cloudticket-server
└─ com.cloudticket.task
   └─ ShowStatusTask        ← P1 开售流转（本文 1.1~1.3）
```

- 类名建议 `ShowStatusTask`（后续可加 `OrderTimeoutTask`、`ReconcileTask`）；
- 方法加日志（`log.info("状态流转：场次 {} 条，演出 {} 条", ...)`），便于排查。
