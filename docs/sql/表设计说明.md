# 云票数据库表设计说明（P1 · 14 张表 · 字段级手册）

> 对应脚本：[001_cloudticket_p1_schema.sql](./001_cloudticket_p1_schema.sql)
> 版本：v1.4（字段级手册）　更新：2026-10-02
> 阅读方式：先看"全局规范"（适用于所有表），再按表查阅。每张表结构为：**定位 → 字段清单 → 索引 → 字段讲解**。

---

## 一、全局规范（所有表的公共约定）

| 规范 | 原因 |
|---|---|
| **逻辑外键**：只存 xxx_id，不建物理外键约束 | 高并发写入时外键检查有开销；一致性由服务层保证（面试常问"为什么不用外键"） |
| **金额一律 DECIMAL(10,2)** | float/double 有二进制浮点误差，钱算不平是事故级 bug |
| **审计四字段**：`create_time / create_user / update_time / update_user` | 由 AuditMetaObjectHandler（MP 内置方法）+ @AutoFill AOP（自定义 XML）自动填充，业务代码禁止手动赋值 |
| **状态字段 tinyint + 注释枚举** | 1 字节省空间；Java 侧用常量类/枚举对应，禁止魔法数字散落在业务代码里 |
| **业务号建唯一索引**：order_no / ticket_no / refund_no / out_trade_no | 唯一索引是幂等的最后一道防线：重复请求插入直接报冲突，代码据此短路 |
| 字符集 utf8mb4 / 引擎 InnoDB | mb4 支持表情昵称；InnoDB 支持事务与行锁 |

## 二、表关系总览

### 2.1 全景图（三条线 + 三类账号）

```
──────────────────────────────────────────────────────────────
 三类账号（谁在用这套系统）
──────────────────────────────────────────────────────────────
merchant(主办方)   ── 建演出、管订单、核销、审退款（数据权限锚点）
user(用户)         ── 浏览、下单、支付、票夹、退票申请
admin(平台管理员)  ── 入驻/演出审核、审计日志查询
        │
        │  三类账号是一切业务动作的发生者，敏感操作都会被旁路记下
        ▼
──────────────────────────────────────────────────────────────
 ① 供给链（货）—— 开售前全部就绪，之后几乎不变（P2 缓存的主战场）
──────────────────────────────────────────────────────────────
merchant(主办方)
   │ 1:N   一个主办方运营多场演出
   ▼
show_info(演出) >── venue(场馆)   N:1 演出挂在某个场馆办
   │
   │ 1:N   一场演出有多个场次（周六场/周日场…），开售时间挂在场次上
   ▼
show_session(场次)
   │
   │ 1:N   一个场次分多个票档（内场VIP/看台A…）
   ▼
ticket_category(票档) ★ 库存真正的家，抢票扣的就是它
        ▲
        │  order_item.category_id —— 供给链与交易链唯一的握手点
──────────────────────────────────────────────────────────────
 ② 交易链（钱与凭证）—— 从下单那一刻开始生长（P3 高并发主战场）
──────────────────────────────────────────────────────────────
user(用户) ──1:N──> orders(订单)
                      │   记录：买卖双方 + 哪一场 + 状态机 + 金额三段式
                      │
                      ├─1:N─> order_item(票位明细·一行=一个票位)
                      │        ├─ 记录"哪个证件买了哪个票档、成交价多少"
                      │        ├─ ★ 实名判重的数据源（覆盖待支付占用）
                      │        └─ category_id 指向票档（与供给链握手）
                      │
                      ├─1:1─> payment(支付流水·钱的账本)
                      │        └─ 回调原始报文存这里，对账对它
                      │
                      └─1:N─> ticket(票·凭证)
                               ├─ 出票 = 票位 1:1 实体化（快照随之复制）
                               ├─ 自带实名快照（人证合一核验）
                               └─ 独立状态流转：有效→核销/退款/作废

refund(退款单) ── 逆向动作：关联 orders（整单退）与 ticket（单张退），
                   退完释放实名名额和库存
──────────────────────────────────────────────────────────────
 ③ 旁路（记账的）—— 不参与业务关系
──────────────────────────────────────────────────────────────
audit_log(审计日志·只追加) —— 记录敏感操作：谁、何时、对什么(target_type+target_id)、
                              做了什么、结果如何、traceId 是多少
```

### 2.2 关系速览（每条关系一行，细讲见第三节）

| 关系 | 类型 | 为什么这么设计 |
|---|---|---|
| venue → show_info | 1:N | 场馆是地点资源，演出是内容，分开管理 |
| show_info → show_session | 1:N | 巡演多天多场次，开售时间按场次独立控制 |
| show_session → ticket_category | 1:N | 按档售票——**售卖精度=库存精度**，库存只能挂最末端 |
| orders → order_item | 1:N | 一单可跨多票档；票位是实名判重的数据源 |
| order_item ↔ ticket | 1:1 实体化 | 票位是"计划"，票是"凭证"，支付后一对一转化 |
| orders → ticket | 1:N | `ticket.order_id` 直接落列关联，**无中间表**（一张票只属于一个订单） |
| orders ↔ payment | 1:1 | 一笔订单一笔成功流水，钱的事实与业务状态分账 |
| orders/ticket → refund | 1:N | 退款支持整单退与单张退两种粒度 |
| user / merchant / admin → audit_log | 旁路 | 三类账号的敏感操作全被记录，追溯出口 |
| user → attendee | 1:N | 用户的"常用观演人通讯录"，可增删改；票上存快照，与其解耦 |

### 2.3 一句话记住整张图

> **三类账号驱动两条线：供给链造货（场馆→演出→场次→票档），交易链花钱（订单→票位→票），order_item 是两条链的握手点，payment 和 refund 管钱的进出，audit_log 在旁边记账。**P4/P5 的 9 张表（优惠券/通知/提醒/积分/社区）将来都从这张图的枝头上长出去，不会出现悬空的表。

## 三、逐表详解

### 1. `user` 用户表

**定位**：C 端登录主体。抢票、会员、积分的归属者。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| phone | VARCHAR(20) | NOT NULL，**唯一** | 登录账号（大陆手机号） |
| password_hash | VARCHAR(100) | NOT NULL | BCrypt 摘要（60 字符，100 留余量） |
| nickname | VARCHAR(50) | NULL | 昵称（抢票播报站脱敏展示） |
| avatar_url | VARCHAR(255) | NULL | 头像 |
| vip_level | TINYINT | NOT NULL，默认 0 | 0 普通 / 1 会员 |
| vip_expire_time | DATETIME | NULL | 会员到期时间 |
| points | INT | NOT NULL，默认 0 | 积分余额（冗余） |
| status | TINYINT | NOT NULL，默认 1 | 0 禁用 / 1 正常 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_phone` 唯一索引。

**字段讲解**：
- **vip_level + vip_expire_time**：会员专享池和退票权益的判断依据。抢票 Lua 脚本要读会员态，所以登录后这两个值会进 Redis 用户缓存，避免每次抢票查库。判断"是否会员"= `vip_level=1 AND vip_expire_time>now()`，两个字段缺一不可——只存等级不存到期时间，续费逻辑就没法做过期降级。
- **points（冗余余额）**：真正的账本是 P5 的 `points_log` 流水表。这里存余额是为了读性能（查积分不用 sum 流水）。**冗余值与流水对不上时以流水为准**，由对账任务校准——"冗余 + 流水 + 对账"这个三件套以后在 sold_count 上还会见到。
- **status**：禁用是"软封禁"，登录拦截时拒绝；数据保留不物理删除。

---

### 2. `merchant` 主办方表

**定位**：B 端主体，数据权限的锚点——主办方只能看自己的演出和订单。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| name | VARCHAR(100) | NOT NULL | 主办方/公司名称 |
| license_no | VARCHAR(50) | NOT NULL，**唯一** | 统一社会信用代码 |
| contact_name | VARCHAR(50) | NULL | 联系人姓名 |
| contact_phone | VARCHAR(20) | NOT NULL，**唯一** | 联系电话（登录名） |
| password_hash | VARCHAR(100) | NOT NULL | 密码摘要（BCrypt） |
| status | TINYINT | NOT NULL，默认 0 | 0 待审核 / 1 正常 / 2 禁用 |
| audit_remark | VARCHAR(255) | NULL | 审核备注（驳回原因回显给主办方） |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_license_no` 唯一；`uk_contact_phone` 唯一。

**字段讲解**：
- **status 状态机**：入驻流程 `待审核 →（平台审核）→ 正常 / 禁用`，流转走条件更新 CAS（`WHERE status=待审核`），重复点击审核只生效一次。
- **audit_remark**：驳回时必填，主办方端能看到——"驳回要给理由"是真实业务的基本礼貌，也是审计闭环的一部分。
- **license_no 唯一**：一个信用代码只能入驻一次，防止重复入驻刷号。
- **contact_phone 登录名 + uk_contact_phone 唯一**：一个手机号只能注册一个主办方账号（v1.2 已并入）。

---

### 3. `admin` 平台管理员表

**定位**：平台侧审核/风控操作员。P1 单角色起步。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| username | VARCHAR(50) | NOT NULL，**唯一** | 登录名 |
| password_hash | VARCHAR(100) | NOT NULL | BCrypt 摘要 |
| real_name | VARCHAR(50) | NULL | 姓名（审计日志展示用） |
| status | TINYINT | NOT NULL，默认 1 | 0 禁用 / 1 正常 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_username` 唯一。

**字段讲解**：
- 初始账号由 SQL 初始化脚本插入（不提供注册接口）——管理后台账号应当由管理员人工开通，而不是公开注册。
- 预留了扩展空间：以后加 `role` 字段做细分角色（内容审核员/财务），P1 单超管不提前设计。

### 4. `venue` 场馆表

**定位**：演出地点。GEO 附近场馆（P6 可选）的数据基础。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| name | VARCHAR(100) | NOT NULL | 场馆名称（同城市内唯一） |
| city | VARCHAR(50) | NOT NULL | 城市（演出筛选维度） |
| address | VARCHAR(255) | NOT NULL | 详细地址 |
| lng | DECIMAL(10, 7) | NULL | 经度 |
| lat | DECIMAL(10, 7) | NULL | 纬度 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_city_name(city, name)` 联合唯一——同城市不得有重名场馆；最左前缀 city 同时覆盖"按城市筛选"的查询，因此**取代了原单列 `idx_city`**（v1.4，不留被覆盖的冗余索引）。

**字段讲解**：
- **lng/lat 用 DECIMAL(10,7)**：7 位小数 ≈ 1cm 精度，够用；为什么不用 float——同样是浮点误差问题，坐标差一点在地图上就偏一条街。
- 场馆数据量极小且很少变更，P2 会整表进 Caffeine 本地缓存（演出详情联表免查库）。
- **维护方：平台管理员**（场馆是全局共享的公共维度资源——无 merchant_id、不在数据权限体系内）；主办方端只提供只读的"可用场馆列表"供创建演出引用；删除有前置引用校验（被演出引用则拒绝）。

---

### 5. `show_info` 演出表

**定位**：内容主体。用户浏览/搜索的对象，主办方运营的核心资产。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| merchant_id | BIGINT | NOT NULL | 主办方（数据权限锚点） |
| venue_id | BIGINT | NOT NULL | 场馆 |
| title | VARCHAR(128) | NOT NULL | 演出标题 |
| category | VARCHAR(32) | NOT NULL | 分类：演唱会/话剧/音乐会/脱口秀/音乐节/其他 |
| cover_url | VARCHAR(255) | NULL | 封面图（OSS 地址） |
| detail | TEXT | NULL | 图文详情（富文本） |
| guide | VARCHAR(1024) | NULL | 观演指南（入场证件/开场时间/交通） |
| status | TINYINT | NOT NULL，默认 0 | 0 草稿 1 待审核 2 驳回 3 审核通过 4 销售中 5 已结束 6 已下架 |
| total_stock | INT | NOT NULL，默认 0 | 总库存（两池之和，冗余校验用） |
| sold_count | INT | NOT NULL，默认 0 | 总销量（冗余） |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`idx_merchant(merchant_id)`、`idx_status_category(status, category)`、`idx_venue(venue_id)`。

**字段讲解**：
- **merchant_id 是数据权限的锚点**：主办方查任何演出/订单，SQL 强制拼 `merchant_id=当前登录方`（@DataScope 注解的过滤字段）。没有它，数据权限就无从谈起。
- **status 七态状态机**：`草稿→待审核→(驳回⇄草稿)→审核通过→销售中→已结束`，旁路"下架"。所有流转条件更新 CAS；"待审核"期间主办方不可编辑（防审核后偷改价格）。
- **idx_status_category 联合索引**：用户端列表查询固定带 `status=销售中`，常按 `category` 筛——最左前缀 status 在前，两列都能吃到索引（索引设计的典型教材案例，面试可讲）。
- **guide 单列**：观演指南是结构化展示的独立内容块，和富文本详情分开，前端渲染方式不同。
- **sold_count 冗余**：P4 攒批合并消费的写入目标（100 条或 1 秒合并一次 UPDATE，吞吐提升十几倍）+ 每日对账校准对象。

### 6. `show_session` 场次表

**定位**：一场演出多天多场次；开售时间挂在场次上，各场次独立开售。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| show_id | BIGINT | NOT NULL | 所属演出 |
| session_name | VARCHAR(50) | NULL | 场次名（周六晚场） |
| session_time | DATETIME | NOT NULL | 演出开始时间 |
| sale_start_time | DATETIME | NOT NULL | 开售时间 |
| sale_end_time | DATETIME | NOT NULL | 停售时间 |
| status | TINYINT | NOT NULL，默认 0 | 0 未开售 / 1 销售中 / 2 已结束 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`idx_show(show_id)`、`idx_sale_start(sale_start_time)`。

**字段讲解**：
- **sale_start_time + idx_sale_start**：开售流转定时任务每分钟扫"到点未开售"的场次——`WHERE sale_start_time<=now() AND status=未开售` 走这个索引。这是"审核通过 ≠ 开售"的关键设计：审核通过只是"获得销售资格"，开售由任务在指定时间放行。
- **status 独立**：演出 status=销售中只代表"有场次在卖"，具体某场开没开看场次自己的状态。

### 7. `ticket_category` 票档表 ⭐（全项目库存主体，最重要）

**定位**：库存真正的家。抢票扣的是它，回补的也是它。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| session_id | BIGINT | NOT NULL | 所属场次 |
| name | VARCHAR(50) | NOT NULL | 票档名（内场 VIP / 看台 A） |
| price | DECIMAL(10, 2) | NOT NULL | 票价 |
| stock | INT | NOT NULL，默认 0 | **公开池**库存（所有人可买） |
| sold_count | INT | NOT NULL，默认 0 | 公开池已售 |
| member_stock | INT | NOT NULL，默认 0 | **会员池**库存（仅会员可买） |
| sold_member_count | INT | NOT NULL，默认 0 | 会员池已售 |
| limit_per_user | INT | NOT NULL，默认 2 | 单用户限购数量 |
| version | INT | NOT NULL，默认 0 | 乐观锁版本号 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`idx_session(session_id)`。

**字段讲解**：
- **双池四字段**：会员先扣 `member_stock`，不足自动转公开池；普通用户只能动 `stock`，碰会员池被 Lua 拒绝（专属错误码）。**回补时必须回到订单记录的 pool_type 对应的池**——四个字段和 orders.pool_type 一一呼应，错池 = 库存账错乱。
- **version 乐观锁**：MP 乐观锁插件生效后，`UPDATE ... SET stock=stock-1, version=version+1 WHERE id=? AND version=?`——CAS 兜底扣减之外的第二道保险，防"丢失更新"。
- **为什么不把库存拆成单独的 inventory 表**：票档数量少（一场最多 5 档），单行更新 + 行锁足够，拆表是过度设计；面试被问"库存分离"时，答"分桶/独立库存表是单行热点进一步加剧后的演进方案"，体现你知道但克制。
- **limit_per_user**：和 attendee 证件判重配合，构成"实名限购"。

---

### 8. `attendee` 观演人表

**定位**：实名制购票的数据基础——"一张票一个证件一个人"。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| user_id | BIGINT | NOT NULL | 所属用户 |
| name | VARCHAR(50) | NOT NULL | 姓名 |
| id_card_no | VARCHAR(32) | NOT NULL | 证件号 |
| phone | VARCHAR(20) | NULL | 联系电话 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_user_idcard(user_id, id_card_no)` 联合唯一。

**字段讲解**：
- **uk_user_idcard 联合唯一**：同一用户录不了重复证件；不同用户可以录同一证件（现实里一家人共用证件的场景由抢票时的"场次级证件判重"拦截——`idcard:{sessionId}` Set）。
- **id_card_no 明文存储的说明**：演示项目从简；生产环境正确姿势 = 加密存储（AES）+ 哈希列做索引（等值查询用哈希，原文解密才取）。SQL 注释里已标注，面试可以主动讲这个安全意识。
- 每用户上限 20 条（服务层校验），防刷表；
- **实名判重不在本表**（v1.3 起）：本表是"通讯录"，可增删改；判重依据是 order_item 里的证件快照——删掉观演人，不影响历史订单的占用判断。

### 9. `orders` 订单表 ⭐（字段最多，每列都有用意）

**定位**：交易核心。状态机、幂等、对账、超时取消全部围绕它。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| order_no | VARCHAR(32) | NOT NULL，**唯一** | 业务订单号 |
| user_id | BIGINT | NOT NULL | 下单用户 |
| merchant_id | BIGINT | NOT NULL | 主办方（数据权限） |
| show_id | BIGINT | NOT NULL | 演出（冗余） |
| session_id | BIGINT | NOT NULL | 场次 |
| order_type | TINYINT | NOT NULL，默认 1 | 1 演出票 / 2 会员开通 |
| pool_type | TINYINT | NOT NULL，默认 1 | 1 公开池 / 2 会员池 |
| amount | DECIMAL(10, 2) | NOT NULL | 原价总额 |
| discount_amount | DECIMAL(10, 2) | NOT NULL，默认 0 | 券抵扣金额（P4） |
| pay_amount | DECIMAL(10, 2) | NOT NULL | 应付金额 |
| coupon_id | BIGINT | NULL | 使用的用户券（P4） |
| status | TINYINT | NOT NULL，默认 0 | 0 待支付 1 已支付 2 已出票 3 已核销 4 已完成 5 已取消 6 退款中 7 已退款 |
| expire_time | DATETIME | NOT NULL | 支付截止时间 |
| pay_time | DATETIME | NULL | 支付时间 |
| out_trade_no | VARCHAR(32) | NULL，**唯一** | 支付渠道单号 |
| cancel_reason | VARCHAR(100) | NULL | 取消原因（超时/用户/风控） |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_order_no`、`uk_out_trade_no`（唯一）；`idx_user_status(user_id,status)`、`idx_merchant_status(merchant_id,status)`（双端列表查询）；`idx_status_expire(status,expire_time)`（超时扫描）；`idx_session`。

**字段讲解**：
- **order_no 唯一索引 = 幂等最后一道防线**：防重 token 拦不住的漏网重复请求，插入时撞唯一索引直接失败，代码捕获转"请勿重复提交"。
- **show_id / merchant_id 是有意冗余**：订单列表页要显示演出名、主办方要做数据权限过滤，如果只存 session_id 每次都要联三张表。冗余字段记录"下单那一刻的关系"，反范式换查询性能——面试讲"冗余的代价是更新时要维护一致性，但订单的关系一旦生成永不变化，所以这里冗余是安全的"。
- **pool_type**：扣减池的账本。取消/超时/退款回补库存时按它回原池；每日对账校准双池。**它是双池模型不错乱的关键**。
- **三段式金额**：amount（原价）→ discount_amount（券抵扣）→ pay_amount（应付），全部服务端重算。支付回调校验"渠道回调金额 == pay_amount"，不一致拒收——防篡改的核心校验。
- **out_trade_no 唯一**：支付渠道回调可能重复投递（网络重试），回调处理先用唯一索引 + `WHERE status=待支付` 条件更新短路，保证"同一笔支付只处理一次"。
- **expire_time + idx_status_expire**：超时取消三重保障之"定时扫描兜底"专用——`WHERE status=待支付 AND expire_time<now()`，联合索引让扫描代价几乎为零。
- **status 八态**：主链路 `待支付→已支付→已出票→已核销→已完成`，分支 `待支付→已取消`、`已支付/已出票→退款中→已退款`。所有流转条件更新 CAS。

### 10. `order_item` 订单票位明细表 ⭐（一行 = 一个票位）

**定位**：记录"这个订单里，哪个证件、买了哪个票档、多少钱"。一行 = 一个票位，**实名判重的数据源**。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| order_id | BIGINT | NOT NULL | 所属订单 |
| category_id | BIGINT | NOT NULL | 票档 |
| unit_price | DECIMAL(10, 2) | NOT NULL | 成交单价（快照） |
| attendee_name | VARCHAR(50) | NOT NULL | 观演人姓名快照（下单时固化） |
| id_card_no | VARCHAR(32) | NOT NULL | 证件号快照 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`idx_order(order_id)`、`idx_idcard(id_card_no)`（实名判重）。

**字段讲解**：
- **unit_price 是"成交快照"**：记录下单那一刻的票价。演出后续调价不影响历史订单金额——金额永远以订单快照为准，这是电商订单的通用铁律。
- **attendee_name / id_card_no 下单时固化**：观演人是用户可增删改的"通讯录"数据，而订单里的"谁"是下单那一刻的事实。快照在**下单时**写入（不能等出票再查观演人表——支付窗口内用户删了观演人，出票就查不到人了）。
- **为什么实名判重查这张表而不是 ticket**：占用的起点是**订单**不是票——待支付期间就占实名名额，否则两人可以同时给同一证件下单、都支付就冲突。判重 SQL：`COUNT(*) FROM order_item oi JOIN orders o ON o.id=oi.order_id WHERE o.session_id=? AND oi.id_card_no=? AND o.status IN (0待支付,1已支付,2已出票,3已核销,4已完成)`——取消(5)/退款(7)状态自动释放名额。
- **quantity 列去哪了**：一行 = 一个票位，某票档的数量 = 该票档的行数；接口层按票档聚合返回 quantity 和 attendeeNames（**前端契约不变**，聚合在后端做）。
- **出票 = 一对一实体化**：支付成功后，每个票位生成一张 ticket，快照字段直接复制。

### 11. `ticket` 票表

**定位**：一张票一行记录；核销、退票、动态二维码都围绕它。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| ticket_no | VARCHAR(32) | NOT NULL，**唯一** | 票号（二维码凭证串的数据源） |
| order_id | BIGINT | NOT NULL | 所属订单 |
| user_id | BIGINT | NOT NULL | 持有人（下单账号） |
| session_id | BIGINT | NOT NULL | 场次（冗余，核销校验用） |
| category_id | BIGINT | NOT NULL | 票档 |
| attendee_name | VARCHAR(50) | NOT NULL | 观演人姓名快照 |
| id_card_no | VARCHAR(32) | NOT NULL | 证件号快照 |
| status | TINYINT | NOT NULL，默认 1 | 1 有效 2 已核销 3 已退款 4 已作废 |
| check_time | DATETIME | NULL | 核销时间 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_ticket_no` 唯一；`idx_order`、`idx_user`、`idx_session_status(session_id, status)`。

**字段讲解**：
- **一单 N 张 = N 行**：出票是支付成功后把 order_item 票位**一对一实体化**成 ticket，票自带实名快照（attendee_name/id_card_no 从票位复制）。每张票独立流转（可以单张退）。
- **attendee_name / id_card_no 快照的用途**：票面是"下单那一刻的事实"——观演人被删改不影响已出票；检票时凭票面证件号做**人证合一核验**（票号 + 入场人身份证比对）。
- **核销 CAS**：`UPDATE ticket SET status=已核销 WHERE ticket_no=? AND status=有效`——影响行数=1 才算核销成功，rows=0 返回具体原因。**一票一核天然幂等**，扫码枪重复扫、手抖点两次都不会重复核销。
- **idx_session_status**：现场统计"该场次已核销多少张"走这个联合索引。
- **session_id 冗余**：核销时要校验"这张票属于当前主办方场次"，有 session_id 就不用联 order 表再联 show 表。

### 12. `payment` 支付流水表

**定位**："钱的事实"账本。订单表是业务状态，这张表是资金流水——对账就是对这两张。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| out_trade_no | VARCHAR(32) | NOT NULL，**唯一** | 商户单号（与 orders 同号，唯一） |
| order_id | BIGINT | NOT NULL | 关联订单 |
| amount | DECIMAL(10, 2) | NOT NULL | 支付金额 |
| status | TINYINT | NOT NULL，默认 0 | 0 待支付 1 成功 2 失败 3 已退款 |
| pay_time | DATETIME | NULL | 渠道侧支付成功时间 |
| callback_time | DATETIME | NULL | 回调到达时间 |
| callback_body | TEXT | NULL | 回调原始报文 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_out_trade_no` 唯一；`idx_order`。

**字段讲解**：
- **callback_body 存原始报文**：验签基于原文（改一个空格验签就失败）、对账基于原文、排查争议也基于原文。**只存解析后的字段等于丢证据**——这是支付模块的老规矩。
- **amount 与 orders.pay_amount 的校验**：回调处理时"渠道回调金额 != pay_amount"直接拒收并告警，防金额篡改。

### 13. `refund` 退款单表

**定位**：退款不是一条 UPDATE，是一个有审核、有渠道交互、有幂等要求的独立单据。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| refund_no | VARCHAR(32) | NOT NULL，**唯一** | 退款单号（幂等） |
| order_id | BIGINT | NOT NULL | 关联订单 |
| ticket_id | BIGINT | NULL | 关联票（整单退为 NULL） |
| amount | DECIMAL(10, 2) | NOT NULL | 退款金额 |
| reason | VARCHAR(255) | NULL | 退款原因 |
| status | TINYINT | NOT NULL，默认 0 | 0 申请中 1 审核通过 2 退款中 3 已退款 4 已拒绝 |
| audit_by | BIGINT | NULL | 审核人 |
| audit_time | DATETIME | NULL | 审核时间 |
| audit_remark | VARCHAR(255) | NULL | 审核备注 |
| create_time / create_user / update_time / update_user | — | 审计四字段 | 见全局规范 |

**索引**：`uk_refund_no` 唯一；`idx_order`、`idx_status`。

**字段讲解**：
- **refund_no 唯一 = 退款幂等**：同一退款单号向渠道重复发起，渠道返回同一笔结果，不会退两次钱；配合本地状态机双保险。
- **ticket_id 单票退**：支持"整单退"和"单张退"两种粒度，所以可空。
- **退票费规则不在表里**：手续费比例是策略（提前 48h 免费 / 48h 内收 X% / 会员免手续费），代码里用策略模式算，表里只存结果金额——规则会变，账不变。

### 14. `audit_log` 审计日志表（只追加）

**定位**：敏感操作"谁在什么时候干了什么"的追溯出口。数据权限、审计两条简历亮点的展示窗口。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK，自增 | 主键 |
| operator_id | BIGINT | NOT NULL | 操作人 id |
| operator_type | TINYINT | NOT NULL | 1 用户 / 2 主办方 / 3 平台 |
| action | VARCHAR(50) | NOT NULL | 动作：MERCHANT_AUDIT / SHOW_AUDIT / REFUND_AUDIT / BATCH_IMPORT / CHECK_IN / … |
| target_type | VARCHAR(30) | NULL | 目标类型（MERCHANT/SHOW/ORDER/REFUND…） |
| target_id | BIGINT | NULL | 目标 id |
| params | TEXT | NULL | 请求参数快照（脱敏后） |
| result | TINYINT | NOT NULL，默认 1 | 0 失败 / 1 成功 |
| ip | VARCHAR(45) | NULL | 操作 IP（45 位兼容 IPv6） |
| trace_id | VARCHAR(32) | NULL | 链路追踪 id |
| create_time | DATETIME | NOT NULL，默认 CURRENT_TIMESTAMP | 操作时间 |

**索引**：`idx_operator(operator_id)`、`idx_target(target_type, target_id)`、`idx_create_time`。

**字段讲解**：
- **没有 update 字段 = 对全局规范的有意豁免**：日志只追加永不修改，天然不需要 update_time/update_user。审计的意义就在于"写了就不能改"。
- **trace_id**：MDC 链路追踪 id，一条审计记录能串回一次完整请求的日志链——排查"谁把这笔单审了"时，从审计跳到全链路日志。
- **params 脱敏后入库**：参数快照含证件号、手机号时要打码，审计日志本身不能变成隐私泄露源。
- 写入方：`@Audit` 注解 + AOP 异步落库（自定义线程池），异步失败不影响主业务但要有告警。
