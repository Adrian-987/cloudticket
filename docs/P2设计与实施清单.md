## 三、分步实施（D1~D5，每步含"操作 + 验证"）

### D1：Redis 接入 + 基线压测（**先拿"没缓存"的数字**）

**操作**
1. `backend/pom.xml` / server pom 引入：`spring-boot-starter-data-redis` + `redisson-spring-boot-starter`；
2. `application.yml`：`spring.data.redis.host/port/database` + 同名占位符风格；真值进 `application-local.yml`；
3. 新增 `config/RedisConfig`：
   - `RedisTemplate<String,Object>`：key 用 String 序列化、value 用 `GenericJackson2JsonRedisSerializer`（**不用 JDK 序列化**）；
   - `StringRedisTemplate` 保留默认（给 ZSet/Lua 用）；
4. 新增 `common/constant/CacheKey`：统一 key 前缀（`cloudticket:...`）；
5. **JMeter 基线**：场景"演出列表 1000 并发 × 10 轮"，记录 QPS / P95 / 错误率（存 `docs/压测记录.md`）。

**验证**：`redis-cli PING` 通；`KEYS cloudticket:*` 为空（还没写缓存）；基线数字入库。

---

### D2：列表缓存 + 详情多级缓存（核心）

**列表（03 §2）**
- key：`cloudticket:show:list:{city}:{category}:{pageNum}:{pageSize}`
- value：`PageResult<UserShowVO>` JSON；TTL 30s + `ThreadLocalRandom` 抖动 0~30s（**防雪崩**）
- 一致性：主办方编辑/审核/下架时**不删**（短 TTL 自然过期，P2 阶段可接受）；P3/P4 再改精确失效

**详情（03 §3）—— 多级 + 逻辑过期 + 布隆**
- 本地：Caffeine `maximumSize=1000, expireAfterWrite=5m`（热点挡在 JVM 内）
- Redis：`cloudticket:show:detail:{id}`，value 包装 `{data, expireAt}`（**逻辑过期**）
- 读流程：
  ```
  ① Caffeine 命中 → 返回
  ② Redis 命中：
       未逻辑过期 → 回填 Caffeine → 返回
       已逻辑过期 → 拿 Redis 互斥锁（SETNX），抢到的异步重建；抢不到直接返回旧值
  ③ Redis miss：
       布隆判断 id 不存在 → 直接返回"演出不存在"（防穿透）
       布隆说可能存在 → 查 DB → 回填 Redis + Caffeine
  ```
- 布隆：`Redisson RBloomFilter`（key `cloudticket:bloom:show`），启动预热全部演出 id
- 验证实验（**大纲要求**）：删掉热点 key → 100 并发同时查 → 日志确认 DB 只被查 1 次（互斥重建生效）

---

### D3：余量缓存 + 热榜

**余量（03 §4）**
- key：`cloudticket:stock:{sessionId}`，Hash：field=categoryId，value=`{stock, memberStock}`
- TTL 3s（允许秒级误差；下单后靠 TTL 自然刷新，**P1 扣减仍走 DB**）
- 读流程：Redis 命中返回；miss 查 DB `session_category_stock` 回填

**热榜（新接口）**
- 契约：`03_演出浏览模块.md` 新增「4. 热门演出 Top10」（GET `/user/shows/hot`，无参，返回 List<UserShowVO>）
- ZSet：`cloudticket:hot:shows:{yyyyMMdd}`，score = 浏览×1 + 销量×10（可调）
- 维护：详情接口浏览时 `ZINCRBY`（异步，失败不影响主流程）
- 查询：`ZREVRANGE 0 9` → 批量查演出（走详情缓存/或批量 SQL）
- 定时：每日零点新建 key（或不建，用当天日期后缀自动切换）

---

### D4：traceId + 耗时统计 + 预热

**traceId**
- `TraceIdFilter`（`OncePerRequestFilter`）：`MDC.put("traceId", UUID.randomUUID().toString().substring(0,8))`，finally `MDC.clear()`
- `application.yml` logback pattern 加 `%X{traceId}`
- 验证：一次请求 → 日志里所有行带同一个 traceId

**耗时统计**
- `@Aspect` 环绕 `@RestController` 方法：记录 `URI + 耗时 + traceId`；>200ms 打 WARN
- （可选）Micrometer 埋点 `http.server.requests`

**预热**
- `ApplicationRunner`（启动）+ `@Scheduled`（每天开售前 5 分钟，可选）
- 动作：① 布隆初始化（所有 show id）② 详情预热（审核通过/销售中的演出）③ 余量预热（当日场次）

---

### D5：虚拟线程 + 三组压测对比 + 报告

**虚拟线程**
- `application.yml`：`spring.threads.virtual.enabled: true`
- 压测对比：同一场景（1000 并发）平台线程 vs 虚拟线程，记录 QPS/P95

**三组压测（核心交付）**
| 组 | 配置 |
|---|---|
| A 直查 | 关缓存（开关或改回 P1 分支）|
| B 单级 Redis | 只开 Redis |
| C 多级 | Caffeine + Redis |

**产出**：`docs/压测记录.md`
```
场景：GET /user/shows/{id}（详情）
A 直查：     QPS=xxx  P95=xxx ms
B 单级Redis：QPS=xxx  P95=xxx ms
C 多级：     QPS=xxx  P95=xxx ms
→ 简历：详情接口 QPS 提升 X 倍，P95 从 A ms 降到 B ms
```

## 四、缓存设计规范（一次性定好，后面照做）

| 项 | 规范 |
|---|---|
| key 前缀 | `cloudticket:` + 业务域 + 对象（`show:detail:1001`）|
| 序列化 | Redis 值用 JSON（Jackson），不用 JDK 序列化 |
| TTL | 列表 30s / 详情逻辑过期 30m / 余量 3s；**全部加随机抖动** |
| 穿透 | 布隆过滤器（演出 id）+ 空值缓存 60s |
| 击穿 | 互斥锁（SETNX）+ 逻辑过期（详情）|
| 雪崩 | TTL 抖动 + Redis 集群（P6）|
| 降级 | Redis 异常 try-catch → 直接查 DB（**缓存故障不拖垮业务**）|
| 一致性 | 写后删缓存（P2 用短 TTL 兜底；P3 双删）|

## 五、风险与注意

| 风险 | 对策 |
|---|---|
| 编辑演出后详情旧数据（最多 5 分钟本地 + 30 分钟 Redis）| P2 可接受（文档写明）；P3 加"编辑后删缓存 + 本地广播"|
| 布隆误判（把存在判成不存在）| 误判率设 1%，定期重建（启动时全量重灌）|
| 本地缓存多机不一致 | 短 TTL（5min）+ P2 不追求强一致 |
| Redis 挂 | 降级直查 DB（try-catch 包住所有缓存读写）|
| 压测数字造假 | **必须真实跑**，记录时间/配置/机器；数字不夸大 |
