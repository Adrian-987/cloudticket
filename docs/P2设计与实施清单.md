### 0.3 要不要锁（项目铁律）

```
优先级：原子操作（Lua） > CAS 条件更新 > 唯一索引 > 分布式锁
```

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 库存扣减 | **Lua** | 锁是排队（吞吐低、超时/死锁）；Lua 一次原子 |
| 订单状态流转 | CAS | 条件更新天然互斥 |
| 支付回调幂等 | 唯一索引 | 插入撞唯一键即幂等 |
| **缓存重建互斥** | **RLock** | 只让一个线程重建（**必须锁**）|
| 多实例定时任务 | RLock/ShedLock | P6 部署多实例时 |

### 0.4 三件套防护对照

| 问题 | 手段 | 落点 |
|---|---|---|
| **穿透**（查不存在的）| 布隆过滤器 + 空值缓存 | 详情（D2-②）|
| **击穿**（热点 key 过期瞬间）| 互斥锁重建 / 逻辑过期 | 详情（D2-②）|
| **雪崩**（大量同时过期）| TTL 抖动 ✅ + 多级 + 高可用 + 限流 | 列表已做抖动 |

## 三、已完成（照着回顾）

### D1 Redis 接入（✅）

**做了什么**

1. `backend/pom.xml`：`redisson.version = 3.50.0`（dependencyManagement 管版本）
2. `cloudticket-server/pom.xml`：排除 `lettuce-core`，引入 `redisson-spring-boot-starter`
3. `application.yml`：`spring.data.redis.host/port/database` = 同名占位符；真值在 `application-local.yml`（`ck.redis.*`）
4. `config/RedisConfig`：
   - 独立 `ObjectMapper`（`JavaTimeModule` + 关时间戳 + `activateDefaultTyping` 写 `@class`）
   - `GenericJackson2JsonRedisSerializer`
   - `RedisTemplate<String,Object>`：key = `StringRedisSerializer`、value = JSON
   - `afterPropertiesSet()`
5. `common/constant/CacheKey`：`PREFIX = "cloudticket:"`、`SHOW_LIST/SHOW_DETAIL/SESSION_STOCK/SHOW_HOT`

**关键决策（面试可讲）**

| 决策 | 原因 |
|---|---|
| 换 Redisson（不用默认 Lettuce）| P2 需要 RLock/RBloomFilter，Redisson 开箱即用；`RedisTemplate` 照常可用 |
| key 用 String、value 用 JSON | key 可读便于排查；JSON 可读、跨语言、体积小 |
| 独立 ObjectMapper（不注入全局）| 全局 mapper 加 `@class` 会污染 HTTP 响应；独立一只互不影响 |
| 为什么必须注册 `JavaTimeModule` | Redis 序列化器自带的 mapper 不认识 `LocalDateTime` → 缓存带时间字段的 VO 直接报错 |

**验证**：启动日志 `Redisson 3.50.0` + `24 connections initialized` + 无 ERROR。

### D2-① 演出列表缓存（✅）

**实现位置**：`ShowServiceImpl.showUserPage`（缓存逻辑）+ `queryUserShowFromDb`（查库复用）

**策略（分层）**

| 查询 | 走缓存？ | 原因 |
|---|---|---|
| 无 keyword 且 pageNum ≤ 50 | ✅ | 有限组合（城市×分类×页），高频复用 |
| 带 keyword | ❌ 直查 | 无限组合/长尾，缓存只会生产废 key（P6 交 ES）|
| 深页（pageNum > 50）| ❌ 直查 | 长尾 |

**Key**：`cloudticket:show:list:{city}:{category}:{pageNum}:{pageSize}`（keyword 必空，不占位）

**TTL**：`30 + ThreadLocalRandom.current().nextLong(30)` → 30~59s 随机（防雪崩）

**降级**：读/写缓存 `try-catch` + `log.warn`（缓存故障不拖垮业务）

**排序**：`ORDER BY s.sold_count DESC, s.id DESC`（热卖优先，id 兜底稳定）

**压测（A 直查 vs B 缓存）**

| 指标 | A | B |
|---|---|---|
| QPS | 754.0 | **1966.8（+161%）** |
| 平均 | 117.1ms | 25.4ms |
| P95 | 780.4ms | **42.1ms（-95%）** |

**已知取舍（已写入契约 03 §2.4）**

- 分页缓存不一致窗口 ≤30s（每个 key 独立 TTL → 变更后"第 1 页新、第 2 页旧"并存）；
- 无击穿互斥（热点 key 过期瞬间可能几十并发查库，数据小可接受）；
- 无主动删缓存（组合太多删不完，靠 TTL）；**版本号方案记 TODO**（变更 INCR → 旧 key 全失效）。

## 四、待做（每步含步骤 + 代码骨架 + 验证）

### D2-② 演出详情：多级缓存（Caffeine + Redis + 逻辑过期 + 布隆 + 互斥）

**目标**：详情接口提速 + 把"三件套"补齐（P2 最重要的一刀）。

**步骤**

1. 加依赖（server pom）：
   ```xml
   <dependency>
       <groupId>com.github.ben-manes.caffeine</groupId>
       <artifactId>caffeine</artifactId>
   </dependency>
   ```
2. 本地缓存 Bean（`config/LocalCacheConfig`）：
   ```java
   @Bean
   public Cache<Long, UserShowDetailVO> showDetailLocalCache() {
       return Caffeine.newBuilder()
               .maximumSize(1000)
               .expireAfterWrite(Duration.ofMinutes(5))
               .build();
   }
   ```
3. 逻辑过期包装（`common/cache/CacheData`）：
   ```java
   @Data
   public class CacheData<T> {
       private T data;
       private LocalDateTime expireAt;   // 逻辑过期时间（不是 Redis TTL）
   }
   ```
4. 读流程（`ShowServiceImpl.showUserDetail`）：
   ```
   ① 本地 Caffeine 命中 → 返回
   ② Redis 命中：
        未逻辑过期 → 回填本地 → 返回
        已逻辑过期 → RLock.tryLock() 抢到 → 异步重建（查库+回填）；
                     抢不到 → 直接返回旧值（不阻塞）
   ③ Redis miss：
        布隆判断 id 不存在 → 返回"演出不存在"（防穿透）
        布隆可能存在 → 查 DB → 回填 Redis（逻辑过期 30m）+ 本地
   ```
5. 互斥重建（关键代码骨架）：
   ```java
   RLock lock = redissonClient.getLock(CacheKey.SHOW_DETAIL + "lock:" + showId);
   if (lock.tryLock(0, 10, TimeUnit.SECONDS)) {     // 拿不到锁立即返回旧值
       try { rebuild(showId); } finally { lock.unlock(); }
   }
   ```
6. 布隆（`config/BloomConfig` + `ApplicationRunner` 预热）：
   ```java
   RBloomFilter<Long> bloom = redissonClient.getBloomFilter(CacheKey.SHOW_DETAIL + "bloom");
   bloom.tryInit(100000, 0.01);          // 容量 10 万、误判率 1%
   // 预热：所有 show id 逐个 bloom.add(id)
   ```
7. 主动失效（编辑/下架时，2 处）：
   ```java
   redisTemplate.delete(CacheKey.SHOW_DETAIL + showId);
   showDetailLocalCache.invalidate(showId);
   ```
8. 余量不进详情缓存（动态数据走单独接口，避免高频失效）

**验证实验（大纲要求，必做）**

```
① 预热详情 → 删除 Redis key → 100 并发同时查同一 id
② 观察：DB 只被查 1 次（互斥重建生效），其余返回旧值或等待
③ 布隆：查不存在的 id（如 999999）→ 直接返回"不存在"，DB 零查询
```

**压测**：详情接口 C 组（多级）vs B 组（单级 Redis）vs A 组（直查 38.7ms / 2312 QPS）。

## 五、缓存设计规范（所有缓存照此写）

| 项 | 规范 |
|---|---|
| key 前缀 | `cloudticket:` + 业务域 + 对象（见 CacheKey）|
| 序列化 | key = String；value = JSON（Jackson，带 @class）|
| TTL | 列表 30~59s / 详情逻辑过期 30m / 余量 3s；**全部加随机抖动** |
| 穿透 | 布隆（详情）+ 空值缓存 60s |
| 击穿 | RLock 互斥重建 / 逻辑过期（详情）|
| 雪崩 | TTL 抖动 + 多级 + 高可用 + 限流 |
| 降级 | 读写全 try-catch + log.warn（缓存故障不拖业务）|
| 一致性 | 短 TTL 兜底；单 key 场景主动删（详情编辑/下架）|

**标准写法模板**（复制改 key 即可）：

```java
try {
    PageResult<UserShowVO> cached = (PageResult<UserShowVO>) redisTemplate.opsForValue().get(key);
    if (cached != null) return cached;
} catch (Exception e) {
    log.warn("读缓存失败，降级查库, key={}", key, e);
}
// ...查库...
try {
    long ttl = 30 + ThreadLocalRandom.current().nextLong(30);
    redisTemplate.opsForValue().set(key, result, ttl, TimeUnit.SECONDS);
} catch (Exception e) {
    log.warn("写缓存失败, key={}", key, e);
}
```

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 编辑演出后详情旧数据（本地 ≤5min / Redis ≤30min）| P2 接受；D2-② 第 7 步做到"编辑即删缓存 + 本地失效"|
