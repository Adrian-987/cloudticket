# 代码与命名规范（项目约束）

> 2026-11-16 定稿。**新增类、改名一律遵守本文**；`AGENTS.md` 已同步约束 AI 生成代码。
> 适用：Controller / Service / Mapper / 实体 / DTO / VO / 枚举。

---

## 一、命名总原则（三层判断）

```
① 这个类只被一个端用？            → 是：加该端前缀（Admin / Merchant / User，放最前）
② 多个端用且结构一致？            → 是：不加端前缀，用业务语义
③ 多个端用但结构不同？            → 是：各端前缀 + 同一语义（三端对齐）
④ 父子嵌套结构？                  → 加语义后缀（Save / Simple / Detail / Remain / Item）
```

**反例对照**：

| ❌ 错误 | ✅ 正确 | 原因 |
|---|---|---|
| `ShowAdminVO` | `AdminShowVO` | 前缀统一在最前 |
| `MerchantPageQuery`（平台查主办方） | `AdminMerchantPageQuery` | 使用方是平台 |
| `UserAdminVO`（平台查用户） | `AdminUserVO` | 同上 |
| `AuditDTO`（平台审主办方） | `MerchantAuditDTO` | 名字太泛，缺语义 |
| `ShowCategoryDTO`（票档） | `ShowSaveCategoryDTO` | 与分类枚举 `ShowCategory` 区分 |

## 二、各层命名规则

| 层 | 规则 | 示例 |
|---|---|---|
| **Controller** | `{端}{模块}Controller`，按端分包 `controller/admin\|merchant\|user` | `AdminShowController`、`MerchantShowController`、`UserShowController`、`AdminAuditLogController` |
| **Service** | 聚合根命名（单数业务名，不按端拆，除非职责确实分离） | `ShowService`（管场次/票档/库存）、`OrderService`（管订单项/票/支付） |
| **Mapper** | **跟实体/主表** | `ShowInfoMapper`、`ShowSessionMapper`、`TicketCategoryMapper`（票档）、`TicketMapper`（票） |
| **实体** | 跟表名；表是复数则类名复数；避开 Java/MySQL 关键字 | `Orders`（表 `orders`）、`ShowInfo`、`SessionCategoryStock` |
| **DTO（入参）** | 动词 + 语义 + `DTO`；查询用 `XxxPageQuery`/`XxxQuery` | `OrderCreateDTO`、`MerchantShowSaveDTO`、`AdminVenueSaveDTO`、`ShowPageQuery` |
| **VO（出参）** | 端前缀（如端特有）+ 语义 + `VO` | `AdminShowVO`、`MerchantShowDetailVO`、`UserShowVO`、`SessionVO`（共用） |
| **子 DTO/VO** | 父语义 + 子语义 + 后缀 | `OrderItemCreateDTO`（订单项）、`ShowSaveCategoryDTO`（演出保存的票档）、`SessionSimpleVO`（场次骨架） |
| **枚举** | 业务概念 + `Status`/`Category`/`Type` | `ShowStatus`、`ShowCategory`、`SessionStatus` |

### 特殊约定

- **"用户概念本身"不加 User 前缀**：`AttendeeVO`（观演人）、`OrderCreateDTO`（下单）—— 这些概念只有 C 端有，加前缀无区分价值；
- **`Show` 二义**：`ShowInfo`（演出实体）、`ShowSession`（场次）、`TicketCategory`（票档）；**不要**用 `ShowCategory` 表示票档（它是分类枚举）；
- **`Ticket` 二义**：`TicketCategory` = 票档定义；`Ticket` = 票（一票一码）。

## 三、校验与分层约定

1. **DTO 校验**：`@NotNull`（包装类型/数字）、`@NotBlank`（字符串）、`@NotEmpty`（集合）、`@Size`（长度/数量）、`@Min/@Max`（数值）；
2. **嵌套集合必须 `@Valid`**：
   ```java
   @NotEmpty @Size(max = 5) @Valid
   private List<OrderItemCreateDTO> items;
   ```
   —— 少了 `@Valid`，子 DTO 的校验全部不生效；
3. **动态规则归 Service**：限购数量、状态机、归属（IDOR）、库存等，**不写在注解里**；
4. **Service 只依赖 Mapper**：子表不单独建 Service（聚合根内访问子表 Mapper）；
5. **接口出参**：枚举字段成对输出 `xxx`（code）+ `xxxDesc`（文案）；用户端文案用 `getUserDesc()`（如 3 → "即将开售"）；
6. **接口文档自包含**：不写"同上/见上文/结构同 03 模块"。

## 四、改名/新增流程（防漏改）

```
1. 新增/改名先对照本文三层判断
2. 全项目搜索旧名（Java + XML + 文档）
3. 同步 XML 的 resultType / resultMap type / parameterType 全限定名（IDEA 改类名不会改字符串）
4. 编译 + 跑回归（7 套脚本，102 项）
5. 提交信息：refactor: 统一 xxx 命名（说明范围）
```

**批量改名的安全做法**：长名优先 + `\b` 词边界（防前缀串改），改完 grep 旧名确认零残留。
